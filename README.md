# MyDialog (`net.omobio.dialogsc`) - on-device root & integrity bypass

An **LSPosed / Xposed module** that neutralises the root/tamper detection and the
Play Integrity gate inside the **MyDialog** self-care app (Dialog Sri Lanka), so
that it keeps working on a rooted device. The module runs **entirely on the
phone** - no PC, no Frida, no terminal needed at use time.

Built and tested on a rooted Samsung SM-A307FN (Android 11, Magisk + Shamiko +
LSPosed 1.9.2), but nothing here is device-specific.

> ### Intended use
>
> This is for running an app **you have installed, on a device you own**, after
> its root detection got in the way. It is not a way to gain access to anything
> you don't already have access to.
>
> **It is almost certainly against the app's terms of service**, and the app
> still talks to its server - only the client-side decision is patched (see
> [Notes](#notes--caveats)). Don't use it on hardware or accounts that aren't
> yours.

---

## TL;DR

1. Build (or grab) `lsposed-module/MyDialogBypass.apk` and `adb install -r` it.
2. In the **LSPosed** manager: *Modules → MyDialog Bypass → Enable module*.
   **MyDialog** is pre-ticked in the scope from the module's `xposedscope`
   metadata - leave **System Framework** unticked.
3. Force-stop MyDialog and reopen it. No reboot required.

Verified working with the module alone (PC disconnected): home screen, live
balance, **My Offers** loading live server data - and it survives app restarts
and a full reboot.

---

## Target app version

The hooks aim at the **obfuscated** internals of MyDialog **18.6.5**. Names like
`b2`, `D1`, `Z1` and the `SecurityValidator` methods are generated by the app's
obfuscator and **change on every release**, so if the app updates and the bypass
silently stops working, this is why. Re-locate the hook targets (see
[What the fix does](#what-the-fix-does)) against the new version.

## Why the app was failing

The Play Integrity part is a dead end, but it turned out **not to be the real
reason** the app refused to run. The app has *two* gates, and the first one is
what actually kills it:

### Gate 1 - root / tamper detection (`MainActivity.Z1()` + `a2()`)

On every start **and every resume** the app runs this on a background thread:

| Check | Looks for | Result on the test device |
|---|---|---|
| `D1()` | `adb_enabled` | **true** (adb is on) |
| `F1()` | developer options enabled | **true** |
| `G1()` / `H1()` / `x1()` / `y1()` | Frida: files in `/data/local/tmp`, `frida-agent` in `/proc/self/maps`, `/` entries, ports 27042-27046, `ps` | **true** while frida-server runs |
| `I1()` | Magisk paths / packages / `magisk` in maps | false (hidden by Shamiko) |
| `M1()` | `/system/bin/su` etc. | false (hidden by Shamiko) |
| `N1()` `J1()` `E1()` `L1()` | taint tracking, monkey, debugger, emulator | false |
| `Utils.e()` | `RootInfoCallable` | false |

If **any** check is true it shows *"Due to new security policy you are not
allowed to use App on rooted devices."* and immediately calls `finish()`.

That is why the app slammed shut instantly instead of reaching the login screen -
and it is also why it happened even with Frida not attached: `adb_enabled` and
developer options are simply on.

### Gate 2 - integrity verdict (`MainActivity.T1()` → `R1()` → `Q1()` → `b2()`)

`b2()` takes the Play Integrity token and POSTs it to the app's backend

```
…/scapp_6_0_1/index.php?r=/scapp/devices/verifyIntegrityToken
```

and reads back `{"success": true|false}`. **The verdict is decided server-side,**
so no combination of TrickyStore/keybox/fingerprint on the device can change the
answer - and the token is an encrypted JWE (`A256KW`/`A256GCM`) that the client
cannot even read. When `success` is false the app shows *"...does not meet the
security standards required for the MyDialog App.."* and exits.

Because the decision is made elsewhere, the only practical fix is to not let the
client act on a "no".

## What the fix does

The module hooks the client side of both gates before the app's first check runs:

* `b2()` → always returns `true` (the server's "no" is ignored)
* the root/tamper checks (`D1 F1 G1 H1 I1 M1 N1 J1 E1 L1 x1 y1 O1`) → `false`
* `A1()` / `B1()` / `U1()` / `V1()` / `W1()` (the "toast + `finish()`" paths) → no-ops
* the JS-facing `SecurityValidator` / `SecurityManager` / `SecurityManagerAdvance`
  helpers (`isSecure`, `performSecurityCheck`, `isProductionSecure`,
  `performComprehensiveSecurityCheck`, `checkFridaLibs`, `checkFridaPort`,
  `checkFridaServer`, `call`, `e`) → report clean

The module is defensive: every hook is looked up by name inside a `try`/`catch`,
so a method that no longer exists after an app update is skipped rather than
crashing the app.

When the module is active you will see this in `logcat` as soon as the app starts:

```
I/LSPosed-Bridge: MyDialogBypass: loading for net.omobio.dialogsc
I/LSPosed-Bridge: MyDialogBypass: hooked b2
...
I/LSPosed-Bridge: MyDialogBypass: armed
```

## The module project

`lsposed-module/` builds a self-contained module APK with no Android Studio:

```
lsposed-module/
├── AndroidManifest.xml                    # xposedmodule + xposedscope meta-data
├── assets/xposed_init                     # entry point: lk.mydialog.bypass.Module
├── res/values/strings.xml                 # app name + xposedscope array
├── src/lk/mydialog/bypass/Module.java     # the hooks
├── build.sh                               # aapt2 + javac + d8 + zipalign + apksigner
└── MyDialogBypass.apk                     # the built, signed module
```

### Requirements

A rooted device with any Xposed-compatible framework that supports **Xposed API
82 or newer** (LSPosed is what this was built against). `build.sh` needs a
**JDK 17** plus an Android **build-tools** directory, an **android.jar** and the
**Xposed API 82** jar.

### Building

Point `build.sh` at those three files with env vars:

```bash
export PATH="$HOME/jdk-17/bin:$PATH"
cd lsposed-module
BUILD_TOOLS=/path/to/build-tools \
ANDROID_JAR=/path/to/android.jar \
XPOSED_API=/path/to/api-82.jar \
./build.sh
```

Defaults are `~/.cache/mydialog/android/{build-tools,android.jar,api-82.jar}`.
The Xposed API 82 jar is not on Maven Central (404) but is available from the
Aliyun mirror:

```
https://maven.aliyun.com/repository/public/de/robv/android/xposed/api/82/api-82.jar
```

`build.sh` generates a throwaway debug keystore on first run, so every clone
signs with its own key - that is fine for a module, but it means the committed
[`MyDialogBypass.apk`](lsposed-module/MyDialogBypass.apk) and one you build
yourself will not have interchangeable signatures. Uninstall before switching.

### Installing

```bash
adb install -r lsposed-module/MyDialogBypass.apk
```

Then enable it in LSPosed as described in the [TL;DR](#tldr).

## Fallback: the Frida route

`run_mydialog.sh` / `bypass.js` / `run_bypass.py` are the original PC-driven
bypass and still work if LSPosed ever breaks. They need the device connected and
rooted, and a terminal kept open:

```bash
pip install -r requirements.txt
./run_mydialog.sh          # Ctrl-C removes the hooks again
```

Notes for that route:

* Frida **cannot spawn** apps on the test device, and attaching right after
  launch loses a race against the ~1.5 s startup check - so `run_bypass.py`
  attaches to the live process first and *then* starts the activity.
* The hooks live only while the script runs. Detach → the app closes itself
  again on the next check (it re-checks on every resume).
* This route needs `frida-server` (arm64) pushed to
  `/data/local/tmp/frida-server16`; it needs root and does not survive a reboot.
  `run_mydialog.sh` tells you if it is missing.
* Frida is version-sensitive - `requirements.txt` pins **16.7.19**. Newer 17.x
  builds crashed on the test device with a `frida_sigchain_compat_validate_signal`
  assertion.

## Notes / caveats

* The app still talks to its backend; the server still sees a Play Integrity
  token that fails its check. Only the client-side decision is patched.
* **Leave `System Framework` unticked in the module's scope.** Only the target
  app should be hooked. Enabling a module for the system framework scope
  crash-looped `system_server` on the Android 11 Samsung device this was built
  on - a bootloop that has to be dug out over adb.
* After changing the scope, force-stop the target app so it re-hooks.
* Root is only needed to *install and configure* this; on a device where root is
  active only during some boots (e.g. Magisk patched into the recovery partition,
  booted via `adb reboot recovery` / Vol-Up+Power), the app works normally on an
  unrooted boot and the module is simply not needed there.
* Using the app this way may go against its terms of service.

## Reverting

**Module off only** - LSPosed manager → *Modules → MyDialog Bypass →* untick
*Enable module*, then force-stop the app.

**Remove everything:**

```bash
adb shell su -c 'pm uninstall lk.mydialog.bypass'
adb shell su -c 'pm uninstall org.lsposed.manager'   # only if you don't want the LSPosed UI
```

The LSPosed framework itself (`/data/adb/modules/zygisk_lsposed`) is part of the
Magisk setup and is left untouched.
